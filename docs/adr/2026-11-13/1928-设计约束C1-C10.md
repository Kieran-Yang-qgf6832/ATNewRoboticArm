# ADR-20261113-1928：设计约束 C1–C10

- 状态：持续有效
- 日期：2026-11-13 19:28（汇总定稿；各条约束的发现时间见下表）
- 相关：[缺陷索引](../../bugs/README.md)

## 背景

这些约束不是“可选的最佳实践”，而是已经用故障、数据或实测换来的设计边界。
把它们集中成一篇 ADR，是为了让“改代码前必须知道什么”只有一个入口；
每条约束都链接回起源缺陷，避免只剩结论、丢了原因。

## 决策

以下每条都是**必须遵守**的约束；违反时优先怀疑实现，而不是先改约束。

---

### C1 零位形处于工作空间边界，不要从那里直接做笛卡尔运动

`reset` 的目标（全零）对应机械臂完全伸直的位形，**雅可比降秩**，位于工作空间边界。
从那里直接做笛卡尔运动，目标不可达。

**做法**：笛卡尔任务务必先 `joint_move` 离开零位形。配置里 `reset_then_cart` 作为反例
保留并注明，可用的参考序列是 `ready_then_cart`。

**实测补充（2026-10-10，更正原先「逆解不收敛」的说法）**

原先这里写「从那里直接做笛卡尔运动，**逆解不收敛**」。实测的失败方式不是这样：

```
[ERROR] Cartesian trajectory REJECTED before any motion: the target is UNREACHABLE —
        the nearest reachable pose is still 0.001109 away from it (IK tolerance is 1.0e-03)
```

即：目标被判定为**不可达**，由 O2 的**下发前预检**拒绝，**一个运动指令都不下发**，
任务层退出码 1。这比「逆解跑到一半失败」安全得多。

离线核实（`tools/ik_solve.cpp`，目标 = 零位姿 + X 5 cm）：

| 目标 | 结果 | 残余 |
| --- | --- | --- |
| 零位姿本身 | Converged | 3.2e-4 |
| 零位姿 + X 5 cm，**零位姿姿态** | **Unreachable** | 1.305636e-03 |
| 零位姿 + X 5 cm，**ready 姿态** | **Unreachable** | 6.96e-03 |

前两行之外还试了 6 个差异极大的初值求解同一个目标，**全部收敛到同一残余
`1.305636e-03`** → 全局不可达，只差约 **1.3 mm**。换成 `ready` 的姿态后残余**更大**，
说明这是**位置**不可达，与姿态约束、与 `|rv| = π` 参数化都无关。

> **注意这个反例很弱**：余量只有 1.3 mm，是**判据边界**案例而不是明显不可行。
> 真正的教训是「零位形在工作空间边界」，不是「零位形一做笛卡尔就炸」。

### C2 控制器状态发布有 500 ms 滞后

`current_state` 参数与 `~/state` 话题由 `ArmController` 的 500 ms wall timer 驱动。任务层任何「切状态后立刻判断」的逻辑都必须先等过该周期（见 F9 的 `state_settle`）。

### C3 轨迹状态 `enter()` 会把轨迹阶段重置为 STOP

`CartTrajState` / `JointTrajState` 的 `enter()` 都会执行 `state = TrajPhase::STOP; traj.stop();`。因此**从任何状态切入都保证轨迹阶段就绪**，`joint_move → cart_move` 可以直接串联，不需要中间插 `idel`。

### C4 保持命令必须基于锁存值

见 F1。任何「保持当前位置」的实现都必须在进入时锁存一次，绝不能每周期重读实测值。

### C5 `yaml_cpp_vendor` 的 CMake 定位不可靠


本机 `yaml_cpp_vendor` 的 ExternalProject 未构建，其 `extras.cmake` 会把 `yaml-cpp_DIR` 指向不存在的路径。必须显式 `find_package(yaml-cpp REQUIRED)` 并链接 `yaml-cpp::yaml-cpp`；且因 `ament_target_dependencies` 使用 plain 签名调用 `target_link_libraries`，不能混用 `PUBLIC`/`PRIVATE`。

### C6 控制器参数必须在 `on_init` 中 `auto_declare`，否则 YAML 里的键被静默忽略

`ArmController::on_init` 用 `auto_declare<...>()` 逐个声明参数（`controller.cpp:126` 起），
之后各处才用 `get_parameter()` 读取。**未声明的键即使写在 YAML 里也读不到**，
`get_parameter()` 返回 `false`，代码取的是 `auto_declare` 里的默认值，
而且**没有任何警告**。

修 O6 时踩到过：第一版只在 YAML 里加了 `gravity_compensation: false` 而没有声明它，
结果开关看起来完全无效，`joint4` 依然停在 −0.005 rad。加一行诊断才看清：

```
idel:   gravity_compensation=true (param found=no)
reset:  gravity_compensation=true (param found=no)
```

**影响**：任何控制器参数写错名字（或改名前忘了同步）都会静默退回默认值。
调 `reset_tolerance` / `default_kp` 这类安全相关参数时，这会导致「改了但没生效」
却毫无提示。

**对策**：新增参数时三处同步——`auto_declare`、YAML、读取处；关键参数建议像
`gravity_compensation` 一样在构造阶段打一行 INFO 把实际生效值打出来。

### C7 不要把辨识输出当成下一轮辨识的先验——不可辨识零空间里的误差会逐轮放大

`reconstruction.prior_source: urdf` 的含义是"用传进来的 URDF 当先验"。辨识问题的可辨识
部分是 36 个基参数（由数据决定），剩下的 24 维落在**零空间**里，完全由先验填充。所以把上一轮
的输出当先验，等于把零空间里的误差原样带进下一轮，而且**只增不减**。

2026-10-13 第三轮 30 次迭代实测（每轮：用上一轮 URDF 生成激励轨迹 → 测 120 s → 辨识 →
把 URDF 写回项目根目录）：

| | 第 1 轮 | 第 30 轮 |
| --- | --- | --- |
| 参数误差 ‖θ−θ_true‖/‖θ_true‖ | 0.29% | **272.7%**（单调上升，Spearman ρ = +1.00，p < 0.001） |
| 总质量 | 6.8055 kg | **18.3928 kg**（真值 6.7966） |
| 数据拟合 rmse | 0.0007 | 0.154（但多数轮次仍在 0.0001 ~ 0.0007） |

**关键是数据拟合一直很好**——很多轮 rmse 只有 1e-4，漂移全发生在不可辨识的零空间里，
所以光看 rmse 完全发现不了，只有拿真值比才看得见。

同一份数据换个先验就能证明这一点（iter 4 / iter 13，关闭投影）：

| 先验 | iter 4 参数误差 | iter 13 参数误差 |
| --- | --- | --- |
| **真值 URDF** | **0.0002%** | **0.0002%** |
| 上一轮辨识输出 | 13.70% | 50.50% |

用真值当先验时辨识几乎是精确的；用上一轮输出当先验就偏 13~50%。
**结论：迭代不会让模型变好，只会让它变坏。** 想改善模型应该去改数据质量（激励轨迹、
真实加速度、时间对齐），而不是把输出反复喂回去。

### C8 `mujoco_plugins` 参数必须写在 `/**` 段，写在 `controller_manager` 下会被静默忽略

`mujoco_ros2_control` 在 controller_manager 进程里**另外创建**一个名为
`mujoco_ros2_control_node` 的节点来承载插件参数，插件加载器是在那个节点上
`list_parameters({"mujoco_plugins"})`。YAML 里按 `controller_manager:` 键写的参数到不了它，
后果是**插件根本不加载**，日志里只有一句容易被忽略的
`No 'mujoco_plugins' parameter found!`。

正确写法见 `src/launch_pack/config/ros2_controller.yaml` 末尾的 `/**` 段
（`vision_camera_plugin`）。这和 C6 是同一类问题：**参数名对、层级错 = 静默失效**。
验证方式是看目标节点：`ros2 param get /mujoco_ros2_control_node ...`，或看插件启动日志里的
`Adding camera: '...'`。

### C9 仿真里的 Python 节点不要开 `use_sim_time`

见 O13：本工程的 `/clock` 是 500 Hz，rclpy 的 TimeSource 订阅它单这一项就吃掉约一个核，
带 GIL 的检测/控制节点会被拖慢一个数量级。**做法**：保持 `use_sim_time=false`，
用消息自带的 `header.stamp`（本来就是仿真时间）作时间基准；
`view` 的 `stamp_from_image:=true` 就是为此加的。

> 这条只针对 Python 侧。`controller_manager`、`robot_state_publisher` 等 C++ 节点
> 仍在用 `use_sim_time=true`，那是正常的。

### C10 仿真相机必须显式写 `resolution`，且 `frame_name` 必须是 optical 帧

两个都会静默出错：

1. `<camera>` 的 `resolution` 默认是 `0 0`，MuJoCo 会回落到 `<global offwidth/offheight>`
   （本场景是 1920×1080）。相机插件按 `fovy` 反推 `K`，分辨率与检测节点
   `camera_info` 的尺寸校验（`intrinsics-size`）绑定，分辨率不对会直接把 PnP 静默禁用。
2. MuJoCo 相机帧是 **X 右、Y 上、光轴 −Z**，ROS 光学帧是 **X 右、Y 下、光轴 +Z**，
   差一个绕 X 的 180°。检测节点只接受 `camera_axis=optical` 的父帧，姿态不对时
   目标 TF 会被禁用。本工程把 180° 固定放在
   `view_sim.launch.py` 的第二段静态 TF（`vision_camera_link → vision_camera_optical_frame`，
   `q=(1,0,0,0)`），第一段 `base_link → vision_camera_link` 直接**解析 MJCF** 的
   `<camera pos/xyaxes>`，保证渲染位姿与 TF 是同一串数字。
