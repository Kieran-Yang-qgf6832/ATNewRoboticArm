# ADR-20261007-0907：任务层采用配置驱动执行器

- 状态：已采纳
- 日期：2026-10-07 09:07
- 相关：[任务层重构设计](0907-任务层重构设计.md)、[实施计划](0912-任务层重构实施计划.md)

## 背景

旧任务层由一组 C++ 任务类组成，新增一个动作或调整一条任务序列都要改代码、重新编译。
机器人演示与调试需要频繁改动作顺序、目标点和等待时间，这种耦合让迭代很慢，也容易把
控制器的实时逻辑和任务编排混在一起。

## 决策

任务层改为**配置驱动的步骤执行器**：

- 任务定义放在 `src/tasks/config/tasks.yaml`，由 `tool` / `points` / `positions` /
  `position_move` / `box_move` / `joint_limits` / `sequences` 组成；
- 步骤类型是一个**封闭集合**，类型属性表集中在 `src/tasks/executor/step_types.cpp` 的
  `step_spec()`；新增任务只改 YAML，新增步骤类型才改 C++；
- 执行器运行在普通 ROS 节点线程，允许阻塞服务调用与内存分配；控制器侧的 FSM 仍然
  只负责实时控制。

## 备选方案

- **保留 C++ 任务类**：类型安全、启动快，但每次改动作都要重新编译，已被实践否决。
- **引入通用脚本/行为树**：灵活，但会引入新的运行时依赖与调试面，且当前动作集合并不大。
- **把任务编排塞进控制器 FSM**：会污染 500 Hz 实时路径，明确不可接受。

## 后果

- 新增目标点、调整序列顺序、改等待时间不需要重新编译；
- 新增步骤类型仍需 C++ 改动，因此步骤词汇表是封闭的；
- YAML 没有编译期检查，键名写错只能在运行时发现（后续需要 schema/单测补强）；
- 实时与非实时路径的边界更清晰：控制器只认 `exp_state` 与轨迹话题。
